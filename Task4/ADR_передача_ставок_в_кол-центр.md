### **Нефункциональные требования**

Опишите здесь нефункциональные требования и архитектурно значимые требования.

| **№** | **Требование**                                                                                                                                   |
|:-----:|:-------------------------------------------------------------------------------------------------------------------------------------------------|
|   1   | Актуальность ставок: обновление не реже одного раза в сутки (соответствует текущему процессу ежедневного обновления ставок).                    |
|   2   | Партнёрский кол-центр получает ставки только файлами (SFTP); API-вызовы со стороны партнёра невозможны.                                          |
|   3   | Доступность сервиса интеграции ставок не ниже 99,9% в часы работы кол-центров.                                                                   |
|   4   | Передача данных по защищённым каналам: REST/HTTPS (TLS) и SFTP (SSH).                                                                             |
|   5   | Избегать доработок ядра АБС подрядчиком (+R-2); передача ставок в кол-центры не требует доработок ядра АБС.                                         |
|   6   | Не создавать прямую нагрузку на ядро АБС: ставки отдаются из rate-service без обращения к ядру АБС (R-2).                                            |
|   7   | Максимально использовать существующие технологии и экспертизу банка (S-1, S-2).                                                                  |
|   8   | Быстрый отклик API ставок (секунды) — для консультации клиента по телефону (P-1).                                                                |
|   9   | Стабильный и согласованный с партнёром формат файла (CSV/XLSX); версионирование и мониторинг доставки файлов.                                     |
|  10   | Мониторинг выгрузки и доставки файлов; контроль «свежести» ставок у партнёра и оповещение при сбоях.                                              |

### **Альтернативы**

Опишите здесь наиболее важные альтернативные решения.

1. **Передавать ставки партнёру по электронной почте (как в текущем процессе, Excel-файлы).** Отклонено: ручной процесс, задержки, риск ошибок и недоставки; при росте числа звонков не обеспечит актуальность и надёжность.
2. **Предоставить партнёрскому кол-центру веб-доступ к реестру ставок.** Отклонено: партнёр работает во внешней информационной системе; ручной ввод данных приведёт к ошибкам и задержкам.
3. **REST API для партнёрского кол-центра.** Отклонено: партнёр не имеет технической возможности выполнять API-вызовы — только файлы.
4. **Получать ставки кол-центру банка через Адаптер АБС (как в текущей интеграции кол-центра с АБС).** Рассмотрено: переиспользовало бы существующий канал, не выставляя rate-service наружу подрядчику. Отклонено: Адаптер АБС создан для обработки заявок (Kafka), а не для отдачи ставок; лишний хоп и нагрузка на АБС-контур при read-only запросе; ставки всё равно пришлось бы читать из rate-service.

**Недостатки, ограничения, риски**

Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. **Файловая передача даёт задержку актуализации.** Ставки у партнёра могут обновляться с лагом (до суток). Требуется мониторинг, версионирование файлов и контроль «свежести».
2. **Зависимость от согласования формата файла с внешней стороной.** Изменение формата требует координации с партнёрским кол-центром.
3. **Безопасность доступа партнёра к SFTP.** Требуется выделенный каталог, минимальные права, ротация ключей и аудит доступа.
4. **Доработка системы кол-центра банка выполняется подрядчиком.** Сроки и стоимость вне контроля банка; возможны задержки.
